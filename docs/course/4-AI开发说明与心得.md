# BaiduNetGo：怎么用 AI 做的，以及心得

## 1 一句话概括

这个项目约 2.1 万行 Go 代码，**几乎全部由 AI 编程助手 Claude Code（模型 Opus 5.5）写出来**。人做的是：定方向、提需求、看效果、挑毛病、做取舍、守底线。6 天里留下了约 50 个 AI 会话记录、103 条 prompt、72 个功能与修复提交和 30 个自动发布的版本，都可以查。初代版本只用了一个 Claude Pro 的 5 小时额度就完成。

模型越来越强，很多以前公认的好 practice 已经用不上了，编程在很大程度上真正成了“许愿式编程”：说清楚要什么，代码交给模型写。

## 2 用了哪些 AI 工具

| 工具 | 用途 |
|---|---|
| **Claude Code**（Anthropic，终端/桌面版编程智能体） | 主力：读代码、规划、写代码、写测试、跑测试、截图看界面、提交推送 |
| Claude Code 的 Skill（技能包） | `design-critique` 做界面设计点评；`task-report` 每个任务结束时生成"任务回执"（改了什么、怎么验证的） |
| Claude Code 的项目记忆 | `CLAUDE.md`（项目知识库）和 memory（个人偏好，例如"改完自己提交推送"） |
| 多会话并行 | 同时开几个 AI 会话做互不相干的任务，每个只提交自己改的文件 |
| 两台电脑加一部手机 | Arch Linux 台式机上开工，让 AI 通过 SSH 配好 MacBook 的开发环境，之后在 Mac 上继续；外出时用手机远程查看会话 |

## 3 工作流程

### 3.1 总体流程

```
① 人：用一两句话说要什么（常带一张截图）
② AI：读相关代码、查依赖库源码，说出打算怎么做
③ 人：确认或纠正方向
④ AI：写代码 + 写测试
⑤ AI：自己验证 —— go test / vet / gofmt；在假网盘上跑界面测试；截图看真实窗口；必要时用真实账号自测
⑥ 人：试用、看截图，挑毛病 → 回到 ①
⑦ AI：按"一件事一个提交"提交、推送 → CI 自动测试并发布新版本
⑧ AI：把这次踩到的坑写进 CLAUDE.md，下次会话自动读到
```

### 3.2 第一句话

整个项目从这样一句话开始（原话）：

> 把 BaiduPCS-Go 和 MyGo 这两个项目结合，给百度网盘搓一个美丽的客户端，要优雅，优雅的动画，优雅的逻辑，以及美丽的不落盘预览（视频也是用 mpv 直接获取链接播放）

接着补了一句"用 Go 原生前端"。AI 据此读了两个库的源码，搭出窗口骨架，然后一块一块地加：登录 → 浏览 → 预览 → 文件操作 → 传输 → 分享 → 设置。

### 3.3 关键一步：让 AI 能自己验证

AI 写代码很快，但**写出来的东西对不对，它得有办法自己看到**。我们专门给它造了几个"眼睛"：

| 手段 | 做法 | 解决什么 |
|---|---|---|
| 假网盘 `internal/fakepan` | 用 httptest 模拟百度全部接口，连"只接受有界 Range""缩略图 URL 每次重新签名"这类怪规则都模拟 | AI 不用真实账号就能跑全部测试 |
| 界面测试 | `ui.Tester` 驱动真实视图点按钮、读结果 | AI 改界面后能确认没改坏 |
| 测试截图 | `BAIDUNETGO_SNAPSHOTS=dir` 输出 PNG | AI 不开窗口也能"看"界面 |
| 窗口截图 | `BAIDUNETGO_CAPTURE=out.png` 运行几秒后截图退出 | AI 能看真实窗口的样子 |
| 真实账号自测 | `BAIDUNETGO_SELFTEST` 在临时文件夹里逐项测全部功能，再清理 | 验证真实环境下能用 |
| 性能统计 | `MYGO_FRAME_STATS=all` | AI 能量出每帧开销，而不是凭感觉 |

### 3.4 项目记忆：CLAUDE.md

AI 每次新会话都不记得上次干了什么。解决办法是一份放在仓库里的 `CLAUDE.md`，每次会话自动读入，里面写着：

- 怎么跑、怎么测、怎么发版
- 架构要点（线程模型、路由、网盘客户端的两条路径……）
- **踩过的坑**，例如"回调不能在持锁时调用，死锁过一次"、"MyGo 只重绘不重建的帧里，建视图时算的东西是静止的"

这份文件人和 AI 一起维护，后来也成了写设计说明书的主要素材。规矩是**同一个错误只纠正一次**：例如有一次 AI 改完没提交，我说“commit，怎么不晓得自己 commit，写进 claude.md，并且记得自动升版本号”，之后每个会话改完都会自己提交、推送，推送触发自动发版。

### 3.5 prompt 是什么样子的

两台电脑上的会话记录统计（截至 10-25）：

| 指标 | 数值 |
|---|---|
| prompt 条数 | 103 |
| 长度中位数 | 22 个字；44 条不超过 20 个字 |
| 带表情的 | 约一半 |
| “优雅”出现次数 | 8 |
| “是人类吗”出现次数 | 3 |

大部分 prompt 不是在下需求，而是在挑问题。几条原话：

- “你做的一点也不优雅呀，你看看 pulse，别人做的多优雅……然后狠狠优化”
- “删除前面会有个 popover，那个挡住我看动效了耶，是人类吗？”
- “更垃圾了，你先别改，你从人类的角度来想想，优雅方案是啥”
- “加那么多废话干啥，跟 gpt 学坏了是吧”
- “mygo 又更新了，看看我们有啥值得更新的”（MyGo 每次更新都这样让 AI 读更新说明，用新特性替掉自己写的旧代码，一共三次）

## 4 真实案例

### 案例 1：截图报 bug，AI 发现不是代码的问题

扫码登录报错，我们只发了一张截图和一句"扫码登录出现这个问题"。AI 没有急着改代码，而是查了正在运行的进程：那个程序是 00:55 打的包，而对应的修复 02:02 才加进来——**跑的是旧版本**。它给出了重新打包和安装的步骤；我们说"我是 Arch"后，它又指出 `.deb` 用不了，改用包里的 `install.sh`。

**心得**：好的 AI 会先查清事实，而不是见 bug 就改代码。

### 案例 2：人发现 AI 的设计不完整

第一版自动测速只测"连接数"一项。我们问了一句："难道这个自动测试只测连接数量，只有这个可以调？应该有许多的。"AI 随后重新设计成五项逐项调优：下载服务器 → 每文件连接数 → 分块大小 → 同时下载数 → 上传连接数，每项都在前一项最优值的基础上测，并定了"90% 最快速度内取最少连接"的推荐规则。

**心得**：AI 会在"能交差"的地方停下来。需求的完整性要靠人来追问。

### 案例 3：一个"全部重绘"的 bug

我们发现删掉一张图片后，所有缩略图都重新加载。AI 查出原因：缩略图缓存用缩略图 URL 做键，而百度**每次列目录都会给 URL 重新签名**，所以每次刷新键全变了。修复是改用"文件 fs_id + 修改时间 + 大小"做键。更重要的是，AI 还让假网盘也按次重新签名 URL，并加了"删一张、其余保留"的测试——**这个 bug 以后不会再悄悄回来**。

**心得**：修 bug 时要同时补上能抓住它的测试，假环境要和真环境一样"刁钻"。

### 案例 4：真实环境才暴露的规则

在假网盘上一切正常，换真实账号后下载和播放却返回 403（小文件偶尔能过）。AI 对真实账号测试不同的请求方式，发现百度下载服务器只接受 `bytes=a-b` 这种有界 Range。于是：所有读取都改成分块；mpv 的 ffmpeg 会发开放式 Range，就写了一个本地流代理（`internal/stream`）把请求拆成有界小块；最后把这条规则也加进假网盘。

**心得**：模拟环境再好也要有真实环境验证；在真实环境学到的东西要回写到模拟环境里。

### 案例 5：让 AI 点评"为什么像 AI 做的"

第一版界面能用，但一看就是 AI 风格。我们用 `design-critique` 技能让 AI 自己截 8 个页面来点评。它的结论很直接：每个元素都套着"现代 UI"的默认模板，却没有一处是专门为网盘做的决定。具体指出了：蓝紫渐变 Logo、漂浮的模糊色团、发光按钮、强调色基本等于 Tailwind 默认的 indigo……还标出了每处在哪个文件哪一行。

之后我们先试了一套暖灰色系（刻度设计系统），最后定为参照 macOS 原生应用 Pulse 的风格：侧边栏毛玻璃材质、彩色图标块、灰色分组面板、系统字体、统一的动效曲线。

**心得**：AI 的审美默认是"平均值"。审美要人来定，但可以让 AI 先当挑刺的评审，帮人说清楚哪里不对。

### 案例 6：AI 做分析，人做决定

"应用占用好多内存，这对吗？"AI 采样了 30 秒，把 377 MB 的 RSS 拆开：约 178 MB 是与其他进程共享的映射文件（显卡驱动、GTK、字体），Go 堆 71 MB、C 堆 58 MB；看不出泄漏。它同时指出一个潜在风险：缩略图用的是百度最大一档（约 850×580），最多缓存 600 张，最坏情况能到 1.5 GB，并给了改法。我们的决定是"先不改"，把它记成后续任务。

**心得**：AI 很适合做测量和分析，但做不做、什么时候做，是人的取舍。

### 案例 7：AI 自己写出的隐藏错误

- **死锁**：传输管理器在持锁时调用 `OnChange` 回调，回调又回读任务列表，结果卡死。修复后在 `CLAUDE.md` 里写明"不要在持有 m.mu 时调用回调"。
- **动画停住**：删除时的粒子动画在鼠标不动时停在半路。原因是 MyGo 有些帧只重绘、不重建视图，而动画进度是在建视图时算的。修复为在绘制时读时间，这条规则也写进了 `CLAUDE.md`。
- **网格跳动**：用框架自带的 GridView 时，窗口一缩放，换行的格子就"跳"过去。AI 读了框架源码，发现 GridView 每行是一个元素，格子换行就会被重建，于是自己写了网格排版，让每个格子从原位置滑到新位置。

**心得**：AI 写的代码一样会有并发、时序方面的隐蔽问题，必须靠测试和真实使用去发现；发现后要写进项目记忆，防止它下次再犯。

### 案例 8：多个 AI 并行

我们常同时开几个会话：一个改网格文件名换行，一个改设置页，一个做自动测速。规矩是**每个会话只提交自己改过的文件**。会话记录里能看到 AI 主动说明"我只提交了这三个文件，`settings_page.go` 和 `tools/` 不是我改的，留在工作区"。

**心得**：AI 并行能成倍提速，但要事先划好边界，否则互相覆盖。

### 案例 9：问“这个测试是对的吗”

GitHub 上的构建失败了，我先让 AI 查原因，接着问了一句：“我觉得有一个更好的问题，这个测试是对的吗？”AI 查下去发现，`TestPathFolds` 写死了 1500 px 和 1250 px 两个窗口宽度，而路径什么时候折叠取决于字体宽度，Linux CI 上的字体更宽，测试就失败了——代码没错，是测试错了。改成用二分法从测量值找出路径和工具栏各自折叠的宽度，并检查工具栏先于路径折叠。

**心得**：测试也是 AI 写的，也要审。红了不一定是代码坏了。

### 案例 10：细节要说到具体

设置页的数字控件，AI 先后改了几版都不对。我最后说：“MB，你不觉得如果直接放在左边，在连接的文字旁边写一个 MB，大家就知道它的单位了嘛？你放在右边不对齐、不统一。”说到这个程度，AI 一次就改对了：单位写在设置名旁边，每个控件都对齐到行尾，数字改成和系统设置一样的预设弹出菜单。

**心得**：“不好看”AI 不知道怎么改；“哪里不对、为什么不对”它能改对。

## 5 人和 AI 各做了什么

| 人 | AI |
|---|---|
| 选题与定位：原生、轻量、不落盘预览 | 读 BaiduPCS-Go 和 MyGo 源码，搞清楚能怎么用 |
| 技术路线：纯 Go、MyGo 原生界面、mpv 播放 | 写出全部模块的代码 |
| 审美与风格：否掉"AI 风"，定 macOS 原生风格 | 自评设计问题、按选定风格重做 |
| 追问需求完整性（测速只测一项？） | 设计算法（逐项调优、90% 规则） |
| 试用、截图报 bug、提供真实账号环境 | 定位原因、修复、补测试 |
| 安全底线：凭据加密、证书校验、许可证 | 实现加密存储、重开 TLS 校验、保留 NOTICE |
| 取舍：先做什么、什么先不做 | 测量与分析，给出选项和代价 |
| 审查与验收 | 自测、截图、写提交说明和更新日志 |

## 6 心得

1. **人从"写代码的"变成"提需求、做判断、做验收的"。** 写代码不再是瓶颈，瓶颈变成了"能不能把要什么说清楚"和"能不能看出哪里不对"。这正是软件工程里需求分析和测试验收的位置。
2. **让 AI 能自己验证，比让它多写代码更重要。** 假网盘、界面测试、截图、自测这些"眼睛"一旦搭起来，AI 就能自己发现和修复大部分问题，人只需要看最后的结果。
3. **文档不再是交差的负担，而是 AI 的工作记忆。** `CLAUDE.md` 写得越清楚，AI 下一次犯的错越少。传统软件工程强调的文档，在 AI 时代反而更有用了。
4. **小步提交、自动发布，让 AI 的高速度可控。** 一件事一个提交、每次推送都跑测试，出了问题能快速定位和回退。
5. **AI 的默认值是"平均值"。** 界面审美、需求的完整性、"够不够好"，AI 都倾向于停在平均水平，需要人不断追问"还能更好吗"。
6. **AI 也会犯错，而且错得很隐蔽。** 死锁、动画停住、缓存失效，都是 AI 写的，也都是靠测试和真实使用发现的。不能因为 AI 写得快就不审查。
7. **真实环境不可替代。** 百度下载服务器的有界 Range 规则，任何文档里都没写，只有在真实账号上跑才知道。

## 7 局限与注意事项

- **代码归属与许可证**：`internal/pcsport` 移植自 BaiduPCS-Go，遵守 Apache-2.0 并保留 NOTICE；依赖库的代码不计入本项目行数。
- **账号安全**：真实账号测试只在临时文件夹中进行并自动清理；测速上传从不合并，不留下文件。
- **AI 给的结论要核实**：AI 的分析（例如内存占用）要看它给出的数据和方法，不能只看结论。
- **成本**：大量使用 AI 编程助手需要付费订阅。

## 8 对软件工程课的启示

AI 没有让软件工程过时，反而让它的每个环节更重要：

| 软件工程环节 | 在 AI 开发中的体现 |
|---|---|
| 需求分析 | 给 AI 的每句话就是需求；说不清，AI 就做不对 |
| 设计 | 架构规则（线程模型、模块边界）写进 CLAUDE.md，AI 才能守住 |
| 测试 | 测试是 AI 能自我纠错的前提 |
| 配置管理 | 小步提交 + 自动发布，控制 AI 的高速度 |
| 项目管理 | 多个 AI 并行要划分边界，就像给组员分工 |
| 文档 | 文档成了 AI 的长期记忆 |

一句话：代码可以交给 AI 写，需求和验收还得自己来。
